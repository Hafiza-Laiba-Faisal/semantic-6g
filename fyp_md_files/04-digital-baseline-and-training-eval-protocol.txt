Perplexity Prompt 6 — Conventional Digital Communication Baseline
I am developing an FYP titled:
“Task-Oriented Deep Joint Source-Channel Coding for UAV Navigation Under Noisy and Fading Wireless Channels.” 

https://www.perplexity.ai/search/8f42ca56-a113-4476-a36b-c61624e11259

The primary DeepJSCC paper does define the architecture of a conventional separated digital system, and it later evaluates a practical JPEG/JPEG2000–LDPC–BPSK/QAM benchmark. It does not define a digital baseline for transmitting a six-dimensional continuous UAV state, so quantizer range/bit depth, framing, selected code/modulation pair, CSI treatment, and controller interface cannot be claimed as taken from that paper.

Quantizer mathematics: what can and cannot be claimed
A fixed-rate scalar quantizer needs a representable range. For coordinate s_i, define an engineering range
[a_i,b_i],\qquad a_i<b_i,
and B_i bits, giving L_i=2^{B_i} reproduction levels.
One common endpoint-inclusive uniform quantizer is:
\Delta_i=\frac{b_i-a_i}{2^{B_i}-1},
q_i=
\operatorname{clip}\left(
\operatorname{round}\left(\frac{\operatorname{clip}(s_i,a_i,b_i)-a_i}{\Delta_i}\right),
0,2^{B_i}-1
\right),
\hat{s}_i=a_i+\Delta_i q_i.
For a non-clipped input and nearest-level rounding, the local granular error obeys
e_i=s_i-\hat s_i,\qquad |e_i|\leq \frac{\Delta_i}{2}.
This is a valid uniform scalar quantizer definition, but it is not specified in Bourtsoulatze et al. The paper normalizes image values to [0,1], then learns a continuous JSCC mapping; it does not quantize source pixels into a fixed B-bit state codebook.[imperial.ac]
Alternative definitions also exist:
A mid-rise uniform quantizer uses 2^B bins and reconstruction values near bin centres; then a common step is (b-a)/2^B, not (b-a)/(2^B-1).
A fixed-point representation is effectively a uniform scalar representation after choosing scale, offset, signedness, and overflow/saturation rule.
IEEE floating-point represents a number through sign, exponent, and significand; it does not provide uniform absolute precision across a declared physical interval.
Vector quantization maps s_t to one codebook index:
q=\arg\min_{j\in\{1,\ldots,2^B\}}\|s_t-c_j\|^2,\qquad \hat{s}_t=c_q.
It can exploit correlation among position, velocity, and goal variables, but requires a specified trained/designed codebook and distortion criterion.
None of scalar uniform, fixed-point, floating-point, or vector quantization is selected by the original DeepJSCC digital comparison for continuous source vectors. NOT SPECIFIED IN THE LITERATURE.
Source-bit count
If six scalars are independently quantized with the same fixed width B, no entropy coding, framing, or metadata, then the raw source payload is algebraically
N_{\rm src}=kB=6B.
This is a conditional bookkeeping identity, not a design selected by the literature.
If each coordinate has its own bit width,
N_{\rm src}=\sum_{i=1}^{6} B_i.
If a vector quantizer uses one B-bit codebook index for the entire state, then
N_{\rm src}=B,
before framing and channel coding. If lossless entropy coding is inserted, payload length becomes variable and need not equal either expression.
The relevant DeepJSCC paper instead treats the image dimension n as “source bandwidth” and maps it directly to k complex channel symbols; it does not establish a 4-, 8-, or 16-bit scalar representation for continuous sources.[imperial.ac]

3. Coding, modulation, and bandwidth accounting
Channel-code mathematics
For a channel code with N_{\rm info} input bits and N_{\rm coded} coded bits,
R_c=\frac{N_{\rm info}}{N_{\rm coded}},
hence, for an unpunctured codeword,
N_{\rm coded}=\frac{N_{\rm info}}{R_c}.
If the source payload plus any outer fields is N_{\rm info}, then this is the appropriate accounting relation. The original DeepJSCC article uses LDPC code lengths:
(4096,8192),\quad (4096,6144),\quad (2048,6144),
where the format is (N_{\rm info},N_{\rm coded}), yielding R_c=1/2,2/3,1/3.[imperial.ac]
However, real coded packets often instead obey:
N_{\rm info}=N_{\rm src}+N_{\rm CRC}+N_{\rm header}+N_{\rm pad},
R_{\rm eff}=\frac{N_{\rm src}}{N_{\rm transmitted\ coded\ bits}},
where R_{\rm eff} differs from nominal R_c because of CRC, padding, termination, tail bits, puncturing, shortening, rate matching, pilots, headers, and retransmission policy. 3GPP’s NR coding standard, for example, explicitly treats transport blocks, CRC processing, and rate matching; it demonstrates why nominal code rate alone is not a complete practical specification.[standards.iteh]

If the coded-bit count is a multiple of m, then
n_{\rm dig}=\frac{N_{\rm coded}}{\log_2 M}
complex modulation symbols are emitted. Under the standard discrete-time complex-baseband model where one constellation symbol occupies one symbol interval, this is also the number of complex channel uses.
If divisibility does not hold, then a framing/padding/rate-matching convention is needed:
n_{\rm dig}=\left\lceil\frac{N_{\rm coded}}{\log_2M}\right\rceil.
The original DeepJSCC paper’s actual practical comparison combines the listed LDPC codes with BPSK, 4-QAM, 16-QAM, and 64-QAM. It does not report a single universal mapping label, Gray-coding choice, constellation coordinate formula, or soft-demapper equation. A common unit-average-energy square-QAM normalization is
\mathbb{E}[|X|^2]=1,
but that specific QAM coordinate scaling cannot be claimed as the original paper’s exact digital-baseline implementation. The paper does state that its experiments set average signal power to P=1, and that for explicitly modulated benchmark schemes, P denotes average constellation-symbol power.[imperial.ac]
Budget equation and fair matching
For a fixed-length quantize–code–modulate chain with no source compression beyond scalar quantization:
N_{\rm src}=6B,
N_{\rm coded}=\frac{N_{\rm info}}{R_c},
n_{\rm dig}
=\frac{N_{\rm coded}}{\log_2M}
=\frac{N_{\rm info}}{R_c\log_2M}.
If N_{\rm info}=6B exactly, then
n_{\rm dig}=\frac{6B}{R_c\log_2M}.
This is a derived accounting identity, not an exact baseline equation stated for UAV states in the literature.
To impose the same nominal complex-symbol budget as a DeepJSCC encoder output z_t\in\mathbb C^n, a frozen digital design would need to satisfy
n_{\rm dig}=n
or explicitly document its rounding/framing surplus. Equivalently, ignoring overhead and integrality,
N_{\rm info}=nR_c\log_2M.
This equation shows why B, R_c, and M cannot be chosen independently under fixed n.
Real-versus-complex dimension: resolved
The original paper defines:
x\in\mathbb{R}^{n_{\rm source}},
\qquad
z\in\mathbb{C}^{k_{\rm channel}},
and calls
\frac{k_{\rm channel}}{n_{\rm source}}
the bandwidth compression ratio. It treats the real and imaginary parts of each complex element z_i as transmitted on the I and Q components, while still counting z_i as one complex channel-input sample/channel use.[imperial.ac]
For your notation, do not reuse n for both state dimension and channel uses. Use, for example:
d_s=6,\qquad z_t\in\mathbb{C}^{n_{\rm ch}}.
Then the direct analogue of the original DeepJSCC convention is
\rho_{\rm DeepJSCC}=\frac{n_{\rm ch}}{d_s}=\frac{n_{\rm ch}}{6}.
There is no extra factor of two if both systems are budgeted in complex channel uses:
n_{\rm DeepJSCC}=n_{\rm digital}.
There is a factor of two if you change the accounting unit from complex uses to real dimensions:
n_{\rm real\ dimensions}=2n_{\rm complex\ uses}.
The important rule is not “always use a factor of two”; it is “never compare one method in complex uses and the other in real dimensions.” The original paper’s k/n convention uses real source dimensions in the denominator and complex channel uses in the numerator.[imperial.ac]
4. Channel models, state recovery, and controller fairness
AWGN: exact DeepJSCC convention
The 2019 journal article defines:
\hat z=z+n,
\qquad
n\sim\mathcal{CN}(0,\sigma^2 I_k),
with average transmit-power constraint
\frac{1}{k}\mathbb{E}[z^\ast z]\le P,
and channel SNR
\mathrm{SNR}=10\log_{10}\left(\frac{P}{\sigma^2}\right)\ {\rm dB}.
It sets P=1 in experiments. For explicitly modulated digital baselines, P is the average constellation-symbol power.[imperial.ac]
This is a complex-baseband SNR per complex symbol convention.
For a coded M-ary scheme with m=\log_2M, nominal code rate R_c, average symbol energy E_s=P, and no overhead,
E_b^{\rm coded\ bit}=\frac{E_s}{m},
E_b^{\rm information\ bit}=\frac{E_s}{R_cm},
so
\frac{E_s}{N_0}
=
R_cm\frac{E_b^{\rm information\ bit}}{N_0}.
Consequently,
\left(\frac{E_b}{N_0}\right)_{\rm info,dB}
=
\left(\frac{E_s}{N_0}\right)_{\rm dB}
-10\log_{10}(R_c\log_2M).
This relation must be adjusted if effective rate includes CRC, padding, pilots, headers, or non-integer symbol packing. General modulation references likewise identify E_s/E_b=\log_2M before coding; the code rate inserts the additional R_c factor when energy is referenced to information bits.[ocw.uc3m]
Slow Rayleigh fading: exact DeepJSCC convention
The original journal article uses:
\hat z=hz+n,
h\sim\mathcal{CN}(0,H_c),
\qquad
n\sim\mathcal{CN}(0,\sigma^2I_k).
For the slow-fading experiment:
h is sampled once per image/frame.
The same h remains constant during transmission of that whole image.
A new independent h is sampled for the next image/frame.
H_c=1.
Neither transmitter nor receiver is assumed to have CSI.
No pilot signals are transmitted.
The average SNR is
10\log_{10}\left(\frac{\mathbb E[|h|^2]P}{\sigma^2}\right).
The term “Rayleigh” refers to the amplitude |h| when h is circular complex Gaussian. [imperial.ac]
For DeepJSCC, no explicit equalizer is included: the neural decoder receives the faded/noisy signal and is trained over this model. The paper suggests that it can implicitly learn channel adaptation/estimation.[imperial.ac]
For a conventional coherent digital receiver, however, practical demodulation and soft LDPC decoding normally require a channel estimate and an equalization/detection rule, for example
\tilde y=\frac{y}{h}=x+\frac{n}{h}
for ideal zero-forcing equalization when h\neq 0. But the original DeepJSCC practical LDPC–QAM benchmark is reported for AWGN, not as a fully specified coherent LDPC/QAM Rayleigh baseline. Its fading “digital” comparison is instead a capacity/outage upper-bound construction that assumes the receiver knows the realization. Therefore:
Conventional fading CSI assumption: NOT SPECIFIED IN THE PRACTICAL DEEPJSCC DIGITAL BASELINE.
Pilot structure: NOT SPECIFIED IN THE LITERATURE.
Equalizer type: NOT SPECIFIED IN THE LITERATURE.
Pilot overhead in bandwidth matching: NOT SPECIFIED IN THE LITERATURE.
BER, BLER, packet error, and task metrics
For transmitted bits b_\ell and recovered bits \hat b_\ell,
\mathrm{BER}
=
\frac{1}{N_{\rm bits}}
\sum_{\ell=1}^{N_{\rm bits}}
\mathbf{1}\{b_\ell\neq \hat b_\ell\}.
For N_{\rm blk} channel-code blocks,
\mathrm{BLER}
=
\frac{1}{N_{\rm blk}}
\sum_{j=1}^{N_{\rm blk}}
\mathbf{1}\{\hat{\mathbf b}^{(j)}\neq \mathbf b^{(j)}\}.
Packet error rate is the same form when “block” is defined as an application packet/frame; symbol error rate is
\mathrm{SER}
=
\frac{\#\{\text{incorrect detected constellation symbols}\}}
{\#\{\text{transmitted constellation symbols}\}}.
BER/BLER are meaningful for the digital baseline because it has an explicit bitstream, coded block, and constellation decisions.
Original unconstrained DeepJSCC has neither a source-bit stream nor a conventional coded-block decision. Therefore, it should not be assigned BER/BLER merely for symmetry. Its appropriate end-to-end outputs are source reconstruction error and navigation/task metrics. The original paper evaluates image reconstruction using MSE/PSNR, not BER, for DeepJSCC.[imperial.ac]

State recovery and controller input
For the proposed scalar quantizer, the digital recovery sequence would be:
\hat b_t
\rightarrow
\hat q_t
\rightarrow
\hat{s}_t=Q^{-1}(\hat q_t)
\rightarrow
\pi(\hat{s}_t)
\rightarrow
u_t.
For endpoint-inclusive uniform reconstruction,
\hat{s}_{i,t}=a_i+\Delta_i\hat q_{i,t},
followed, if desired, by saturation to [a_i,b_i].
This is a valid derived digital-system construction. The original DeepJSCC paper has the analogous source-decoder relationship “decoded compressed bitstream \rightarrow JPEG/JPEG2000 decompression \rightarrow\hat{x},” but does not write Q^{-1}(\hat b) for state vectors.[imperial.ac]
Same controller: fairness classification
Using the same controller/policy \pi after each method’s received representation is a sensible experimental approach only if the controller’s input space is identical.
Digital and reconstruction DeepJSCC naturally fit:
\pi(\hat{s}_t).
A task-oriented representation r_t may have a different dimension and semantics:
\pi(r_t).
Thus, claiming “the exact same controller” is only valid if r_t is deliberately defined to have the same interface as \hat{s}_t, or if \pi is a shared architecture trained/evaluated under an explicitly matched representation contract.
Whether one frozen controller should be reused, retrained per method, or co-trained end-to-end is a PROJECT-SPECIFIC FAIRNESS DESIGN CHOICE. The DeepJSCC image paper has no navigation controller; the task-oriented edge-inference work does not establish a closed-loop UAV-controller fairness rule.[imperial.ac][linkedin]

Which components require training:

Data usage:
Training: Used to update neural network weights via gradient descent.
Validation: Used for hyperparameter tuning (e.g., learning rate, early stopping) and model checkpoint selection. Never used for final performance reporting. [Standard practice]
Testing: Used only once after final model selection to report unbiased performance metrics. [Standard practice]
Test Episode Consistency:

B. UAV Episode/Data Generation
Structure:
Recommendation: Option 2 (Complete navigation episodes/trajectories).
Reasoning: DeepJSCC is evaluated on its ability to support a closed-loop task. Independent state vectors (Option 1) ignore temporal correlation and control dynamics. Task-oriented communication (Diao et al.) explicitly optimizes for the success of a trajectory or sequence of actions, not just single-step reconstruction. [Supported by Diao et al. (2024, 2025) which use trajectory/control losses over time steps.]
Training Sample Content:
A single training step for the communication system typically processes a batch of state vectors $s_t$ (or images) at a specific time $t$.
However, the loss function aggregates error over the episode or uses the state transition $(s_t, u_t, s_{t+1})$ to compute task success.
Specific Structure: For Task-Oriented training, the sample is effectively the episode sequence ${s_0, s_1, \dots, s_T}$ and actions ${u_0, \dots, u_{T-1}}$, as the loss (e.g., goal-reaching error) depends on the cumulative effect of communication errors over time. [Project-specific design choice, aligned with Diao et al. control loops.]
C. Initial and Goal Position Generation
Best Practices:
Randomization: Start positions ($p_{start}$) and Goal positions ($p_{goal}$) should be sampled uniformly within a defined operational area (e.g., a 2D square region). [Standard practice]
Distance Constraints:
Minimum Distance: Enforce $|p_{start} - p_{goal}| \ge d_{min}$ (e.g., 5–10 meters) to prevent trivial "already there" episodes.
Maximum Distance: Enforce $|p_{start} - p_{goal}| \le d_{max}$ to ensure the goal is reachable within the episode time limit $T$ given max velocity $v_{max}$.
Velocity Initialization: Typically $v_0 = $ (hovering start) for simplicity, or sampled from a low-velocity distribution. [Project-specific design choice][0]
Literature Note: Specific values for $d_{min}, d_{max}$ are rarely universal constants in communication papers; they are simulation parameters. You must define these based on your UAV kinematic limits ($v_{max}, u_{max}$) and episode length $T$. [Project-specific design choice]
D. Navigation Controller During Dataset Generation
Controller Definition:
Fixed Controller: Use a fixed, lightweight controller (e.g., PD or PID) for all methods during evaluation to ensure fairness. The controller should take the received/reconstructed state $\hat{s}_t$ (or task representation) as input and output control $u_t$. [Standard practice]
Training Architecture:
Reconstruction DeepJSCC: Train $f_\theta, g_\phi$ to minimize $|s_t - \hat{s}_t|^2$. The controller is not part of the training loop (open-loop communication training). [Directly specified by Bourtsoulatze et al. (2019)]
Task-Oriented DeepJSCC: Train $f_\theta, g_\phi$ (and optionally controller parameters) to minimize a task loss (e.g., goal error). The controller must be differentiable (or use a surrogate) to backpropagate gradients through the loop: $s_t \to \text{Channel} \to \hat{s}t \to \text{Controller} \to u_t \to s{t+1}$. [Directly specified by Diao et al. (2024, 2025)]
Isolation: The controller logic (gains, structure) must remain identical across Conventional, Reconstruction, and Task-Oriented evaluations. Only the input to the controller (quantized vs. reconstructed vs. task-feature) changes. [Standard practice]
E. Train / Validation / Test Split
Strategy:
Split Unit: Split by episodes, not by individual state vectors.
Reasoning: States within a trajectory are temporally correlated ($s_{t+1}$ depends on $s_t$). Splitting states randomly would cause data leakage (training on $s_t$ and testing on $s_{t+1}$ from the same episode), inflating performance. [Standard practice]
Protocol: Generate $N$ episodes. Assign indices $0 \dots 0.7N$ to Train, $0.7N \dots 0.85N$ to Val, $0.85N \dots N$ to Test. [Standard practice]

Handling:
Frozen: Test episodes must be generated once with a fixed seed and saved (or regenerated with the same seed).
No Tuning: No hyperparameters, model checkpoints, or algorithm choices may be selected based on Test performance. [Standard practice]
Implementation: In code, generate test_seeds at the start of the project and hardcode them. Use a separate eval_loop that loads the final model and runs only on this set. [Standard practice]
G. Random Seeds
Best Practice:
Seeds to Set: Python random, NumPy np.random, PyTorch torch.manual_seed, and CUDA torch.cuda.manual_seed_all. Enable torch.backends.cudnn.deterministic = True if reproducibility is critical (note: may impact performance). [Standard practice]

Training Seed: Controls weight initialization, batch shuffling, and training channel noise realizations.
Evaluation Seed: Controls test episode generation (start/goal positions) and test channel noise realizations.

I. Training SNR Strategy
Strategies in Literature:
Strategy 1 (One model per SNR): Original DeepJSCC (Bourtsoulatze et al., 2019) often trained separate models for specific SNRs (e.g., 0dB, 5dB, 10dB) to maximize performance at that point. [Directly specified by Bourtsoulatze et al. (2019)]
Strategy 2/3 (SNR Range / Random SNR): Later works (Kurka & Gündüz, 2021; Xu et al., 2022) introduced SNR-adaptive training where SNR is sampled randomly per batch (e.g., $SNR \sim \mathcal{U}$ dB). Recommendation:

For Baselines: You may train Reconstruction DeepJSCC at specific SNRs if you want to show the "best case" for that baseline, but a single SNR-range model is fairer for comparison. [Project-specific design choice]

Evaluation:
Fixed Values: Test SNR values (e.g., ${-5, 0, 5, 10, 15, 20}$ dB) must be fixed in advance.
Mismatch: Models trained on an SNR range (e.g., 0–20 dB) can be evaluated at any SNR within or slightly outside that range. Models trained at a single SNR (e.g., 10 dB) will show the "cliff effect" when tested far from 10 dB.
Reporting: Report performance across the full test SNR range to show the SNR-vs-Performance curve. [Standard practice]
